# WhatCook («Что приготовить?») — Context for AI Agents

Этот файл автоматически считывается AI-агентом при каждом обращении. В нем содержится актуальный контекст проекта, архитектурные решения, правила разработки и кодовая база.

---

## 1. О проекте
* **Название**: WhatCook («Что приготовить?»).
* **Суть**: Мобильное PWA-приложение для людей, которые хотят рационально использовать продукты в холодильнике, не допускать порчи еды и быстро находить подходящие рецепты с автоматическим формированием списка покупок для недостающих ингредиентов.
* **Форм-фактор**: **Mobile-First PWA** (приоритет мобильных экранов смартфонов, мобильные шторки, свайпы, возможность установки на экран, работа в режиме `standalone`).
* **Сетевая модель**: **Гибридная (Online-First + Offline-Fallback)**.
  * Обязателен интернет: регистрация/авторизация, синхронизация данных между устройствами, обновление каталога рецептов, push-уведомления.
  * Работает офлайн: просмотр сохраненных/открытых рецептов во время готовки на кухне, список покупок в магазине со слабой связью.

## 2. Архитектура и стек технологий

### 2.1. Репозиторий
* **Монорепозиторий (Monorepo)**:
  * `frontend/` — клиентское SPA/PWA на Vue 3.
  * `backend/` — REST API сервер на Golang.
  * `docs/` — проектная документация ([`docs/tech-stack.md`](docs/tech-stack.md)).
  * `docker-compose.yml` — оркестрация локальных сервисов (PostgreSQL, бэкенд, фронтенд).

### 2.2. Frontend
* **Фреймворк**: Vue 3 (Composition API, `<script setup>`, TypeScript).
* **Сборщик**: Vite.
* **Среда выполнения и пакетный менеджер**: **Bun** (всегда используйте `bun` для управления зависимостями, сборки и запуска скриптов).
* **Мобильный UI**: **Vant UI** (готовые мобильные компоненты: `SwipeCell`, `ActionSheet`, `DatePicker`, `PullRefresh`).
* **Стейт-менеджер**: Pinia.
* **Роутинг**: Vue Router 4.
* **PWA & Кэш**: `vite-plugin-pwa` (Workbox) + **IndexedDB (Dexie.js)** для офлайн-хранения инвентаря и покупок.

### 2.3. Backend
* **Язык**: Golang (Go 1.22+).
* **Веб-фреймворк**: **Gin** (REST API).
* **СУБД**: **PostgreSQL 16+**.
* **Слой данных (ORM/Query)**: **SQLC + pgx** (чистый SQL компилируется в типобезопасный Go-код).
* **Миграции БД**: **`golang-migrate`** (`backend/migrations/*.up.sql` и `*.down.sql`).
* **Документация API**: **Swagger / OpenAPI** (библиотека `swaggo/gin-swagger`, UI доступен на `/swagger/index.html`).
* **Медиафайлы & Оптимизация**: локальное хранилище `backend/uploads/recipes/` (раздается через Gin и прокси Vite, изолировано через интерфейс `Storage`, встроенная билинейная оптимизация 512x512 и JPEG сжатие Quality 75).
* **Нейросетевой пайплайн рецептов**:
  * Источник: датасет аутентичных русскоязычных рецептов `russian-recipes-parser`.
  * Интеллектуальный нормализатор: **Sber GigaChat API** (канонические русские названия ингредиентов, критичность `основной`/`важный`/`опциональный`, расчет сложности и времени, генерация гастрономических англоязычных промптов `image_prompt`).
  * Генерация ресторанных обложек: нейросеть **FLUX.1** с детерминированным кэшированием по SHA-256 хэшу названия блюда.
* **Авторизация**: JWT (Access Token в заголовке `Authorization: Bearer`, Refresh Token в защищенной `HttpOnly` куке).
* **Уведомления**: Web Push API (VAPID) через фоновый воркер/cron в Go (`SherClockHolmes/webpush-go`) для напоминаний о сроках годности продуктов.

## 3. Правила для агента при генерации и изменении кода

1. **Mobile-First UX**: Любой UI-код во фронтенде должен быть протестирован под узкие экраны смартфонов (от 360px), иметь удобные touch-зоны (минимум 44x44px) и не ломаться на мобильных экранах.
2. **Типизация**: Везде использовать строгий TypeScript во фронтенде и строгие типы в Go (никаких нетипизированных `any` / `interface{}` без крайней необходимости).
3. **Безопасность SQL**: Все запросы к PostgreSQL должны генерироваться через SQLC или параметризоваться через `pgx` (никакой склейки строк для предотвращения SQL-инъекций).
4. **Офлайн-устойчивость**: Логика работы с продуктами в холодильнике и списком покупок должна учитывать возможность отсутствия сети (сохранение в Pinia + Dexie.js с фоновой синхронизацией).
5. **Документирование эндпоинтов**: При создании каждого нового хэндлера в Go обязательно писать Swagger-аннотации (`// @Summary`, `// @Tags`, `// @Success`, `// @Router`), чтобы спецификация `/swagger/index.html` была актуальной.
6. **Строгий фокус на MVP (No Over-engineering)**:
   * Реализуем **исключительно функционал MVP**. Любые идеи «на вырост» (семейные аккаунты/Household, мульти-списки, распознавание чеков/фото продуктов камерой, сканирование штрихкодов, платная подписка и биллинг) явно **исключены из скоупа разработки**.
   * Кодовая база, схема БД и API должны оставаться компактными, понятными и не содержать неиспользуемых абстракций.
7. **Обязательное использование DTO (Data Transfer Objects)**:
   * Все входящие запросы (Request DTO) и исходящие ответы (Response DTO) API строго типизируются отдельными структурами в пакете `internal/dto`.
   * Модели базы данных (SQLC) никогда не отдаются напрямую в HTTP-ответы и не принимаются из тела запроса. DTO отвечают за валидацию входящих полей (`binding:"required"` и др.) и форматирование данных для клиента.
8. **Тестирование бэкенда на Go (Testify)**:
   * Для всех модульных и интеграционных тестов в Go обязательно используется библиотека **`testify`** (`github.com/stretchr/testify/assert` и `github.com/stretchr/testify/require`).
   * Использование `testify` обеспечивает единообразие ассертов, читаемые сообщения об ошибках и чистый код тестов без повторяющихся проверок `if err != nil`.
9. **Минимум комментариев в коде (Clean & Self-Documenting Code)**:
   * Писать как можно меньше комментариев в коде. Не комментировать очевидные вещи, тривиальные функции и структуры.
   * Код должен быть чистым и самодокументируемым за счет понятного нейминга функций, переменных и типов.
   * Комментарии допустимы только там, где они функционально необходимы: Swagger-аннотации (`// @Summary`, `// @Router` и т.д.) или действительно нетривиальная бизнес-логика.
10. **Фиксация завершения этапов разработки**:
    * Каждый раз, когда пользователь говорит или подтверждает, что этап закончен, агент обязан:
      1. Обновить статус выполненного этапа в [`docs/roadmap.md`](docs/roadmap.md) (отметка `✅ Завершен` и чекбоксы `[x]`).
      2. Зафиксировать изменения в git через коммит с описанием выполненных задач.
11. **Обязательный прогон линтеров в конце каждого этапа**:
    * По окончании реализации каждого этапа агент обязан прогонять тесты (`go test ./...`) и линтеры (`go vet ./...`, а также `golangci-lint run ./...` при поддержке тулчейном), исправляя все замечания до сдачи этапа.
12. **Разработка в отдельных git-ветках**:
    * Каждый этап разработки реализуется в отдельной ветке git (формат: `feat/b<номер>-<название>` или `feat/f<номер>-<название>`).
    * При подтверждении завершения этапа изменения фиксируются коммитом в ветке этапа, пушатся в `origin`, а затем вливаются в `master`.
13. **Обновление версии приложения перед публикацией изменений**:
   * Перед каждым коммитом и push с завершёнными изменениями обновлять версию WhatCook по SemVer: patch для исправлений, minor для новой функциональности, major для несовместимых изменений.
   * Синхронно менять `frontend/package.json` и отображаемую версию в `frontend/src/views/ProfileView.vue`.

## 4. Продуктовая логика и доменные правила (MVP)

1. **Каталог рецептов и источник данных**:
   * База рецептов сформирована на основе аутентичного русскоязычного датасета (`russian-recipes-parser`) с нормализацией через Sber GigaChat и генерацией ресторанных фуд-фотографий через FLUX.1.
   * Стартовый сид миграции содержит 50 сбалансированных блюд с локальными оптимизированными обложками.
   * Фоновый воркер `RecipeWorker` в Go поддерживает инжест и нормализацию новых рецептов порциями с соблюдением лимитов API.
2. **Гибкий учет количества продуктов**:
   * Пользователь не обязан знать точные граммы. В схеме поддерживается как точное количество (`amount` + `unit`), так и качественная оценка/флаг наличия (`in_stock` / `approximate_quantity: много, средне, мало`).
   * Алгоритм сопоставления рецептов в первую очередь проверяет сам факт наличия ключевых ингредиентов.
3. **«Базовая корзина» по умолчанию**:
   * Базовые ингредиенты (соль, сахар, вода, растительное масло, черный перец) считаются имеющимися дома по умолчанию и не блокируют возможность приготовить блюдо.
   * Пользователь может персонализировать базовую корзину в настройках профиля.
4. **Модель доступа (MVP)**:
   * 1 пользователь = 1 персональный инвентарь холодильника и 1 список покупок (прямая связь по `user_id`, без промежуточных таблиц семей).
5. **Продукты-исключения (Аллергены / Непереносимость)**:
   * 1 бесплатный продукт-исключение на пользователя (хранится прямо в профиле пользователя). Рецепты с этим ингредиентом исключаются из подбора.
