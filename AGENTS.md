# WhatCook («Что приготовить?») — Context for AI Agents

Этот файл автоматически считывается AI-агентом при каждом обращении. В нем содержится актуальный контекст проекта, архитектурные решения, правила разработки и кодовая база.

---

## 1. О проекте
* **Название**: WhatCook («Что приготовить?»).
* **Суть**: Мобильное PWA-приложение для людей, которые хотят рационально использовать продукты в холодильнике, не допускать порчи еды и быстро находить подходящие рецепты с автоматическим формированием списка покупок для недостающих ингредиентов.
* **Форм-фактор**: **Mobile-First PWA** (приоритет мобильных экранов смартфонов, мобильные шторки, свайпы, возможность установки на экран, работа в режиме `standalone`).
* **Сетевая модель**: **Гибридная (Online-First + Offline-Fallback)**.
  * Обязателен интернет: регистрация/авторизация, синхронизация данных между устройствами, обновление каталога рецептов, push-уведомления.
  * Работает офлайн: просмотр сохраненных/открытых рецептов во время готовки на кухне, список покупок в магазине со слабой связью.

## 2. Архитектура и стек технологий

### 2.1. Репозиторий
* **Монорепозиторий (Monorepo)**:
  * `frontend/` — клиентское SPA/PWA на Vue 3.
  * `backend/` — REST API сервер на Golang.
  * `docs/` — проектная документация ([`docs/tech-stack.md`](docs/tech-stack.md)).
  * `docker-compose.yml` — оркестрация локальных сервисов (PostgreSQL, бэкенд, фронтенд).

### 2.2. Frontend
* **Фреймворк**: Vue 3 (Composition API, `<script setup>`, TypeScript).
* **Сборщик**: Vite.
* **Пакетный менеджер**: **pnpm** (всегда используйте `pnpm` для управления зависимостями).
* **Мобильный UI**: **Vant UI** (готовые мобильные компоненты: `SwipeCell`, `ActionSheet`, `DatePicker`, `PullRefresh`).
* **Стейт-менеджер**: Pinia.
* **Роутинг**: Vue Router 4.
* **PWA & Кэш**: `vite-plugin-pwa` (Workbox) + **IndexedDB (Dexie.js)** для офлайн-хранения инвентаря и покупок.

### 2.3. Backend
* **Язык**: Golang (Go 1.22+).
* **Веб-фреймворк**: **Gin** (REST API).
* **СУБД**: **PostgreSQL 16+**.
* **Слой данных (ORM/Query)**: **SQLC + pgx** (чистый SQL компилируется в типобезопасный Go-код).
* **Миграции БД**: **`golang-migrate`** (`backend/migrations/*.up.sql` и `*.down.sql`).
* **Документация API**: **Swagger / OpenAPI** (библиотека `swaggo/gin-swagger`, UI доступен на `/swagger/index.html`).
* **Медиафайлы**: локальное хранилище `backend/uploads/` (раздается через Gin, изолировано через интерфейс для будущего перехода на S3).
* **Авторизация**: JWT (Access Token в заголовке `Authorization: Bearer`, Refresh Token в защищенной `HttpOnly` куке).
* **Уведомления**: Web Push API (VAPID) через фоновый воркер/cron в Go (`SherClockHolmes/webpush-go`) для напоминаний о сроках годности продуктов.

## 3. Правила для агента при генерации и изменении кода

1. **Mobile-First UX**: Любой UI-код во фронтенде должен быть протестирован под узкие экраны смартфонов (от 360px), иметь удобные touch-зоны (минимум 44x44px) и не ломаться на мобильных экранах.
2. **Типизация**: Везде использовать строгий TypeScript во фронтенде и строгие типы в Go (никаких нетипизированных `any` / `interface{}` без крайней необходимости).
3. **Безопасность SQL**: Все запросы к PostgreSQL должны генерироваться через SQLC или параметризоваться через `pgx` (никакой склейки строк для предотвращения SQL-инъекций).
4. **Офлайн-устойчивость**: Логика работы с продуктами в холодильнике и списком покупок должна учитывать возможность отсутствия сети (сохранение в Pinia + Dexie.js с фоновой синхронизацией).
5. **Документирование эндпоинтов**: При создании каждого нового хэндлера в Go обязательно писать Swagger-аннотации (`// @Summary`, `// @Tags`, `// @Success`, `// @Router`), чтобы спецификация `/swagger/index.html` была актуальной.

## 4. Продуктовая логика и доменные правила (MVP)

1. **Каталог рецептов и интеграция с API**:
   * Рецепты импортируются/синхронизируются через внешний кулинарный API (например, Spoonacular / TheMealDB) с кэшированием в локальную базу PostgreSQL.
   * Предусмотреть слой локализации/перевода рецептов и названий ингредиентов на русский язык.
2. **Гибкий учет количества продуктов**:
   * Пользователь не обязан знать точные граммы. В схеме поддерживается как точное количество (`amount` + `unit`), так и качественная оценка/флаг наличия (`in_stock` / `approximate_quantity: много, средне, мало`).
   * Алгоритм сопоставления рецептов в первую очередь проверяет сам факт наличия ключевых ингредиентов.
3. **«Базовая корзина» по умолчанию**:
   * Базовые ингредиенты (соль, сахар, вода, растительное масло, черный перец) считаются имеющимися дома по умолчанию и не блокируют возможность приготовить блюдо.
4. **Модель доступа (MVP)**:
   * 1 пользователь = 1 персональный инвентарь холодильника и 1 список покупок. Архитектура связей в БД проектируется с возможностью будущего объединения пользователей в «Семью» (Household).
